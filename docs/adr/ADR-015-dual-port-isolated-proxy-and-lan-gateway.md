# ADR-015: 本地代理双端口物理隔离与局域网安全暴露策略

## 状态
已接受 (Accepted) - 2026-10-21 (具体化与落地 ADR-006)

## 背景与上下文
在跨平台流媒体播放与投屏中，本地代理既需要为本机 libmpv 播放器提供本地 NAS (SMB/NFS) 的 Range 解码和 CCTV H5e 密钥动态改写，又需要为远端智能电视提供 DLNA 投屏拉流出口（CAST-03），并支持手机扫码远程配置门户。
若直接将单端口代理监听于 `0.0.0.0`，在公共 Wi-Fi 或多网卡（VPN/虚拟机）环境下将导致 NAS 凭据与媒体流完全暴露，且容易遭受内网 SSRF 探测攻击。

## 决策
1. **双端口物理隔离架构**：
   - **`LoopbackStreamProxy` (固定 127.0.0.1:9978)**：
     - 常驻运行，专门服务于本机 libmpv 播放引擎；
     - 承载 CCTV TS 密钥解密重写与本地 NAS (SMBv2/NFSv3) Range 流桥接；
     - 严格绑定 IPv4 回环接口，永不对外部物理网卡开放，不需要操作系统入站防火墙权限。
   - **`LanGatewayServer` (按需物理网卡 IP 监听，动态端口或 9979)**：
     - **按需拉起**：仅当用户触发“DLNA 投屏”或进入“手机远程配置”页面时临时启动，空闲超时自动关闭；
     - **随机短效 Token**：投屏生成的媒体流 URL 采用强随机 UUID v4 Token，仅白名单允许当前媒体，并在投屏会话终止时即刻注销；
     - **配对码鉴权 (Pairing PIN)**：远程配置 Web 门户强制要求大屏端显示的 6 位动态随机配对码换取短期 Bearer Token，所有配置写入 API 必须校验有效 Token。
2. **沉淀至独立纯 Dart 包**：
   - 将双服务实现从 `apps/juying_app` 彻底解耦，下沉沉淀至 `packages/proxy_server/`，以便脱离 Flutter 框架进行纯命令行单元测试与抓包回放测试。

## 权衡与后果
- **收益**：本机日常播放具备零外部网络攻击面；局域网投屏与远程配置在最小权限与强鉴权保护下受控运行。
- **代价**：需要管理两个独立 HttpServer 实例及其生命周期，投屏服务在多网卡设备上需实现物理网卡优选策略。
